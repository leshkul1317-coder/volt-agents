# Часть 4. Аналитика, воронка, A/B, CRO — ВОЛЬТ (90 дней)

> Автор части: агент-аналитик. Контекст: прокат APEXWOLT, Красноярск,
> сайт **volt-rent.netlify.app** (статика на Netlify) → заказ-бот-курьер
> в Telegram (создаёт и подтверждает заявку) + отдельный саппорт-бот.
> Ключевая особенность архитектуры: **сайт не хранит заказ целиком** —
> решение "оформить" происходит в Telegram, поэтому главный аналитический
> вызов 90 дней — сшить сессию сайта с событием в боте.

## 1. Модель метрик

### Северная звезда (North Star Metric)

**Подтверждённые аренды (выдачи инструмента) в неделю** — считаем по
статусу «выдан» в боте-курьере. Это метрика, которая честно отражает и
работу воронки (трафик→заявка→подтверждение), и логистику (выдача), и
качество спроса (не просто «написали в бот», а реально забрали
инструмент).

Вторая метрика-компаньон (обязательно смотреть рядом, иначе NSM можно
накрутить разовыми клиентами): **доля повторных аренд за 90 дней**.
Рост числа выдач без роста повторных аренд = утечка в удержании, а не
победа роста.

### Метрики по этапам воронки

| Этап | Метрика | Определение |
|---|---|---|
| 0. Трафик | Сессии, пользователи, каналы (source/medium) | Стандартные сессии Яндекс.Метрики, с разбивкой по UTM |
| 1. Карточка товара | Просмотры карточки, CTR карточка→клик CTA | `product_view` / клики по кнопке «Арендовать» |
| 2. Заявка (лид) | Начатые заявки, отправленные заявки | Клик по CTA, ведущий в Telegram-бот (deep-link), считается «заявка начата»; `bot_start` с валидным payload = «заявка начата в боте» |
| 3. Заявка оформлена | Заполненные заявки в боте | Бот получил все обязательные поля (товар, срок, адрес/пункт выдачи, телефон) — `order_request_created` |
| 4. Подтверждение курьером | Confirm rate | Оператор/курьер подтвердил наличие и слот — `order_confirmed` |
| 5. Выдача (аренда началась) | Rental issued | Инструмент фактически выдан — `rental_issued`, дата, срок, тариф |
| 6. Возврат | On-time return rate | Возврат в срок vs просрочка — `rental_returned`, `rental_overdue` |
| 7. Повтор | Repeat rate 30/60/90 дней | Тот же клиент (телефон/Telegram ID) оформил новую заявку после возврата |

**Правило**: каждая метрика должна вести к решению. Не считаем «лайки
на пост» как метрику воронки — это фидовая, не продуктовая метрика (её
место в отчёте SMM-части).

## 2. Как считать: настройка трекинга под Netlify + Telegram-боты

Ключевая инженерная задача 90 дней — **сквозная связка «сайт → бот»**,
потому что Telegram не передаёт referrer/UTM автоматически. Ниже
практичная схема без сложного стека.

### 2.1 Веб-аналитика на сайте

- **Яндекс.Метрика** — основной инструмент (аудитория РФ, вебвизор,
  карта скроллов, электронная торговля). Ставится через тег в `<head>`
  на Netlify (статический сайт — просто вставка кода счётчика в шаблон,
  без задержек деплоя).
- GA4 — опционально, вторым слоем, если понадобится сверка или в
  будущем таргетинг через Google Ads. На старте не обязателен —
  не плодим лишние счётчики без решения, которое они закрывают.
- **Цели (Метрика) / события**, минимальный набор:
  - `product_view` — просмотр карточки инструмента (авто по URL-шаблону `/tool/*`)
  - `cta_rent_click` — клик по кнопке «Арендовать» / «Оформить заявку» на карточке
  - `cta_telegram_click` — клик по любой кнопке, ведущей в Telegram (бот-заказ)
  - `tariff_switch` — переключение тарифа (сутки/3 дня/неделя/месяц) на карточке
  - `phone_click` / `support_bot_click` — обращения в саппорт-бот
  - `scroll_75` — прокрутка карточки на 75% (индикатор дочитывания условий аренды/залога)

### 2.2 UTM-схема каналов

Единый формат, нижний регистр, без пробелов, фиксируем в
общем гугл-таблице «UTM-реестр ВОЛЬТ»:

| Параметр | Значение | Пример |
|---|---|---|
| utm_source | канал | `vk`, `yandex`, `google`, `telegram`, `avito`, `2gis`, `qr_offline` |
| utm_medium | тип трафика | `cpc`, `organic`, `social`, `referral`, `print`, `email` |
| utm_campaign | кампания | `perforator_launch`, `90days_brand` |
| utm_content | вариант креатива/кнопки | `hero_cta`, `banner_v2` |
| utm_term | ключевое слово (для платного поиска) | `arenda_perforatora_krsk` |

Правило: **ни одна ссылка не публикуется без UTM** — офлайн (QR на
пункте выдачи), в шапке VK/Telegram-канала, в подписи блогера, в
объявлении Avito/2ГИС.

### 2.3 Как сшить заявку из бота с источником трафика (главный кусок)

Telegram deep-link поддерживает параметр `?start=` (до 64 символов,
только буквы/цифры/`_`/`-`). Схема на 90 дней — по нарастающей сложности:

**Фаза 0–30 (быстрый старт, без разработки):** свой `start`-код на
каждый канал/кампанию вручную, например:
`t.me/volt_order_bot?start=vk_ads01`, `t.me/volt_order_bot?start=qr_pv_bratsk`.
Бот логирует `start_param` вместе с заявкой в таблицу (Google
Sheets/Airtable) — этого достаточно, чтобы понимать **источник на уровне
канала/кампании** (без креатива и без сессии сайта).

**Фаза 31–60 (точная сшивка сайт→бот):** на кнопках CTA сайта вместо
прямой ссылки — переход через лёгкую Netlify Function
(`/api/go-to-bot`), которая:
1. читает текущие UTM сессии (уже в query/сторадже после перехода на сайт),
2. генерирует короткий click-id, пишет строку `click_id → utm_source/medium/campaign/content/term + timestamp` в таблицу/лёгкую БД (Airtable/Google Sheets/Supabase — что уже есть в стеке),
3. редиректит на `t.me/volt_order_bot?start=<click_id>`.

Бот при `start=<click_id>` подтягивает UTM из той же таблицы по
`click_id` и пишет их в карточку заявки. Это тот же принцип, что
identify-merge в веб-аналитике («анонимный визит → известное
событие»), только вручную реализованный поверх Google Sheets — без
лишних инструментов это самый дешёвый способ для статического сайта.

**Фаза 61–90:** свести бот-лог и Метрику в один недельный дашборд
(п. 5), проверить схождение цифр (сколько `cta_telegram_click` в
Метрике vs сколько `bot_start` с валидным `click_id` в логе бота —
разница = потери на переходе/недоверие к Telegram).

### 2.4 События бота (лог в таблицу — минимум полей)

`timestamp | user_id_hash | click_id/utm | товар | тариф | срок | адрес/ПВЗ | статус (создана/подтверждена/выдана/возвращена/просрочена) | сумма (демо, если есть) | залог | повтор_клиента (да/нет)`

Хэшируем `user_id`/телефон для приватности в аналитических выгрузках,
исходные данные остаются только в самом боте/CRM для операционки.

## 3. Воронка оформления заказа: где теряем, гипотезы

Реалистичная карта потерь для модели «сайт → deep-link → бот»:

| Переход | Типичная потеря | Гипотеза причины |
|---|---|---|
| Главная → Каталог/категория | Не находят нужный инструмент | Слабая навигация по категориям, нет фильтра «что нужно сделать» |
| Каталог → Карточка | Низкий CTR по карточкам | Нет фото в работе, непонятна цена/наличие с первого взгляда |
| Карточка → Клик CTA | Главная точка потери в проекте такого типа | Не видно сразу: цена по тарифам, размер залога, условие доставки от 3 дней — человек уходит «подумать» и не возвращается |
| Клик CTA → Открытие Telegram | Потеря на переходе в другое приложение | Нет анонса «сейчас откроется бот, это быстро», страх незнакомого бота, отсутствие prefill (кто выбрал инструмент — должен не вводить всё заново) |
| Открыт бот → Заявка заполнена | Отвал на заполнении полей | Слишком много вопросов бота подряд, нет прогресс-бара/понимания сколько шагов осталось |
| Заявка → Подтверждение курьером | Задержка ответа оператора | Нет автоответа с ожидаемым временем подтверждения → человек уходит к конкуренту |
| Подтверждение → Выдача | Срыв слота доставки | Нет SMS/сообщения-подтверждения времени, нет отображения бесплатной доставки от 3 дней как стимула увеличить срок аренды |
| Выдача → Возврат в срок | Просрочки, конфликты по залогу | Неясные условия залога на входе → сюрприз на выходе |
| Возврат → Повтор | Нет повторной активации | Разовая транзакция, не остаётся в контакте (нет вовлечения в саппорт-бот/канал после возврата) |

### CRO-оптимизации (Quick wins → Приоритет)

**Карточка товара**
- Цена по всем тарифам (сутки/3 дня/неделя/месяц) видна без скролла, с выделением самого выгодного варианта.
- Бейдж «Бесплатная доставка по Красноярску от 3 дней» рядом с ценой, а не в футере/условиях.
- Явное отображение размера залога (даже если «по запросу» — фраза «залог возвращается полностью при возврате в срок» снимает главную тревогу).
- Статус наличия («в наличии / 2 шт. на завтра») — снижает уход «подумать».
- Один основной CTA («Арендовать») + один второстепенный («Спросить в чат») — без визуальной конкуренции кнопок.

**Переход в бот**
- Deep-link с prefill: `?start=` кодирует товар+тариф, бот сразу говорит «Вы выбрали Перфоратор APEXWOLT, 3 дня» — не заставляет вводить это текстом.
- Микро-текст под кнопкой: «Оформление за 1 минуту в Telegram, без звонков» — снижает тревогу «зачем мне открывать мессенджер».

**Форма/флоу в боте**
- Максимум 4–5 шагов (товар подтверждён → срок → адрес/ПВЗ → телефон → подтверждение), с явным счётчиком «шаг 2 из 4».
- Автоответ бота сразу после заявки: «Ответим за X минут» (снимает тревогу ожидания, X — то, что реально можете держать).
- Кнопки вместо свободного ввода везде, где это возможно (выбор тарифа/ПВЗ — inline-кнопки, а не текст).

**После возврата**
- Автосообщение через 1 день после возврата: короткий опрос (1 клик — «всё понравилось / были проблемы») + мягкое приглашение в канал/на повторную аренду со скидкой на новый инструмент.

## 4. A/B-тесты: 4–6 гипотез с приоритизацией ICE

ICE = (Impact + Confidence + Ease) / 3, шкала 1–10 по каждому.

| # | Тест | Гипотеза | Метрика (primary) | Impact | Conf. | Ease | ICE |
|---|---|---|---|---|---|---|---|
| 1 | CTA-кнопка на карточке: «Арендовать» vs «Оформить заявку за 1 минуту» vs «Написать в Telegram» | Явное обещание скорости/простоты повышает клики сильнее, чем нейтральный глагол | CTR карточка → `cta_telegram_click` | 8 | 6 | 9 | 7.7 |
| 2 | Бейдж доставки/залога на карточке: показывать условия «бесплатная доставка от 3 дней» + «залог возвращается полностью» рядом с ценой vs текущее размещение в блоке условий | Снятие тревоги о деньгах прямо у кнопки увеличит долю кликов по CTA | CTR карточка → CTA, доля заявок с тарифом ≥3 дней | 7 | 7 | 8 | 7.3 |
| 3 | Тарифная сетка: подсветка рекомендованного тарифа («3 дня — выгоднее, доставка бесплатно») vs плоский список тарифов без акцента | Визуальная подсказка «лучшего» тарифа сдвинет выбор в сторону более длинной и выгодной для бизнеса аренды | Доля заявок с тарифом 3+ дня, средний срок аренды | 7 | 6 | 7 | 6.7 |
| 4 | Deep-link с prefill товара/тарифа в бот vs обычный `start` без данных (пользователь вводит всё заново) | Prefill сократит отвал на этапе заполнения заявки в боте | Conversion `bot_start` → `order_request_created` | 7 | 8 | 5 | 6.7 |
| 5 | Автоответ бота со временем подтверждения («Ответим за 15 минут») vs без явного SLA | Явный SLA снизит отвал в ожидании подтверждения курьером | Conversion `order_request_created` → `order_confirmed` | 7 | 6 | 8 | 7.0 |
| 6 | Заголовок оффера на главной: слоган «Сила в аренду» vs выгодо-ориентированный вариант с конкретикой (демо-цифра, пометить как демо до утверждения реальной цены) | Конкретное обещание (цена/срок) конвертит лучше имиджевого слогана на холодном трафике | CTR Главная → Каталог/Карточка | 6 | 5 | 9 | 6.7 |

**Порядок запуска** (по ICE, с поправкой на зависимости): #1 и #2 —
фаза 0–30 (не требуют разработки, только вёрстка/копирайт); #5 — тоже
0–30 (текст автоответа бота, дёшево); #3 — 31–60; #4 — 31–60 (требует
Netlify Function из п. 2.3); #6 — можно в любой момент, но логично
после того, как заголовок и оффер утвердит маркетолог/копирайтер (не
дублируем их часть — здесь только measurement-план теста).

**Sample size**: сайт новый, точного трафика нет — на старте (фаза
0–30) используем эвристику по глубине воронки, а не строгий расчёт
мощности: копим минимум 2–3 недели данных на вариант или ~200+
кликов по CTA на вариант, что бы ни наступило раньше, и ориентируемся
на направление эффекта, а не на p<0.05 при малых числах. Строгую
статзначимость по калькулятору (Evan Miller) применяем начиная с
фазы 31–60, когда появится базовый трафик за 30 дней для оценки
базовой конверсии.

Каждый завершённый тест фиксируем в **плейбуке экспериментов**
(гипотеза → результат → % изменение → вывод → «применить ли шаблон в
других местах»), чтобы через 90 дней иметь не 6 разрозненных тестов, а
библиотеку паттернов, которые работают на аудиторию Красноярска.

## 5. Дашборд: еженедельный отчёт

Источники: Яндекс.Метрика (сайт) + таблица бота (заявки/статусы) —
свести в один Google Sheets/Looker Studio дашборд, обновление раз в
неделю (по понедельникам, за предыдущую неделю).

**Блок 1. Трафик**
- Сессии всего, по каналам (source/medium)
- Доля прямого/брендового трафика (сигнал «работает ли офлайн/сарафан»)

**Блок 2. Продуктовая воронка**
- Просмотры карточек, топ-5 карточек по просмотрам
- CTR карточка → `cta_telegram_click`
- Заявки начаты (`bot_start`) vs заявки оформлены (`order_request_created`) — потеря на заполнении

**Блок 3. Операционная воронка (из бота)**
- Заявки → подтверждено (confirm rate), среднее время подтверждения
- Подтверждено → выдано (issue rate)
- Возвраты в срок vs просрочки

**Блок 4. Юнит-показатели по тарифам**
- Распределение заявок по тарифам (сутки/3дня/неделя/месяц)
- Средний срок аренды, доля заявок с бесплатной доставкой (3+ дня)

**Блок 5. Удержание**
- Повторные аренды за 30/60/90 дней (% от базы клиентов с завершённой арендой)
- Топ-5 клиентов по числу аренд (кандидаты в «профи»-сегмент для отдельного оффера)

**Блок 6. Эксперименты**
- Активные A/B-тесты, статус, промежуточный сигнал (без «победителя» до набора выборки)

Простая схема потока данных:

```
Сайт (Метрика: сессии, цели, UTM)
        │
        ▼
Клик CTA → Netlify Function (click_id + UTM) → лог-таблица
        │
        ▼
Telegram-бот (start=click_id) → дозаполняет UTM → пишет заявку/статусы в ту же таблицу
        │
        ▼
Еженедельная сводка (Google Sheets/Looker Studio) → отчёт по 6 блокам выше
```

## 6. Удержание, повторные аренды, снижение оттока

В прокате нет «подписки» и «отмены», поэтому классический cancel-flow
неприменим напрямую — адаптируем логику под цикл «аренда → возврат →
пауза → новая аренда».

**Определение «оттока» для ВОЛЬТ**: клиент считается «спящим», если
не оформлял новую заявку **90 дней** после последнего возврата
(ориентир, из-за сезонности ремонта/дачи можно уточнять с апреля-мая,
когда цикл короче). Это не подписка — фиксируем не как «отмену», а
как окно для win-back коммуникации.

**Когорты для еженедельного/ежемесячного просмотра**
- По месяцу первой аренды (когортный retention curve: сколько % когорты вернулось за 30/60/90 дней)
- По сегменту: частник (разовая/сезонная аренда, дача/ремонт) vs профи (частая аренда, стройка/отделка/автосервис) — разная частота, разный оффер удержания
- По каналу привлечения — какой канал даёт более «повторного» клиента (важно для CAC-решений, см. также распределение бюджета в части маркетолога)
- По инструменту первой аренды — какие категории (перфоратор/УШМ/шуруповёрт) чаще приводят к повтору

**Прокси-«health score» для профи-сегмента** (вместо SaaS-скора
использования — сигналы вовлечённости):
- Частота аренд за 90 дней (RFM-подход: Recency/Frequency последних аренд)
- Возврат в срок без конфликтов по залогу (плохой опыт с залогом — сильный анти-сигнал повтора)
- Реакция на сообщения саппорт-бота (открывает/отвечает — вовлечён)

Высокий скор → кандидат на персональный B2B-оффер (постоянная аренда
для бригады/автосервиса, отдельный менеджер). Низкий скор после
первой аренды без возврата → приоритет для follow-up после возврата.

**Точки удержания на 90 дней**
- Сообщение через 1 день после возврата: короткий опрос + мягкое приглашение вернуться (п. 3)
- Напоминание за 1 день до окончания срока аренды (снижает просрочки → лучше опыт → выше вероятность повтора)
- Сегментированный win-back через саппорт-бот/канал на 45–60 день молчания (не спам, ценностное сообщение: новый инструмент в парке, сезонное предложение)
- Отдельная ветка для профи-сегмента: предложение долгосрочной/повторяющейся аренды (это тема для маркетолога/оффера, здесь — сигнал, что сегмент существует и его видно в данных)

**Метрики удержания в дашборд**
- Repeat rate 30/60/90 дней (динамика по неделям)
- Средний интервал между арендами (для профи vs частников)
- Доля «спящих» клиентов, к которым запущен win-back, и отклик на него
